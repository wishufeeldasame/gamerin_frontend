### A-1. 일반 설정 화면이 저장하지 않는데 "저장되었습니다"

- **상태**: 방향 확정
- **저장소**: frontend
- **담당**: C (레포 이슈 FE-9)
- **원칙(사용자 지시)**: 개발 중인 프로젝트이므로 하위호환, 임시 숨김, 현 사용자 배려용 처리는 하지 않는다.

**배경**
`/settings` 저장이 서버 요청 없이 localStorage와 클라이언트 상태만 바꾸는데 "변경사항이 저장되었습니다."를 표시한다. 가짜 email/phone 기본값(`user@gamerin.com`, `+82 10-1234-5678`), handle 편집으로 인한 프로필 링크 오염, 저장 키에 userId 없음, `JSON.parse` 예외 처리 없음, 계정 삭제 라벨 오해 등이 겹쳐 있다. 프라이버시·알림 설정은 로컬에만 저장되는데 프로필 페이지가 보는 사람의 로컬 설정으로 남의 프로필 표시를 결정한다. 백엔드에는 `PATCH /api/v1/users/me`(nickname, bio, profileImageUrl, coverImageUrl, location, website)만 있고 handle·email·phone·프라이버시·알림 설정·로그인 상태의 비밀번호 변경·계정 삭제 API는 없다(비로그인 비밀번호 재설정 `/api/v1/auth/find-password`, `/reset-password`는 있다).

**수정 방향 (사용자 결정, 2026-10-01)**
1. **Edit Profile에서 수정하는 항목은 설정 화면에서 제외한다.** (닉네임/표시 이름, 소개, 위치, 웹사이트, 프로필·커버 이미지는 프로필 편집 모달로 일원화. 설정 화면에서 `PATCH /users/me`를 호출하지 않는다.)
2. **프라이버시 설정 섹션을 제거하고, 그 설정을 읽는 프로필 페이지의 로컬 비공개 로직도 제거한다.** 제거 대상: `privacySettings` state와 동기화 effect(`profile/[userId]/page.tsx:348,385-396`), `showStats`로 전적 탭을 숨기는 조건(`:996`), `profilePublic`으로 비공개 안내를 보여주는 분기(`:1150`). 결과적으로 프로필은 항상 공개로 표시된다. **알림 설정 섹션도 함께 제거한다**(앞선 결정).
3. **가짜 email 기본값(`user@gamerin.com`)을 제거하고 빈 칸으로 둔다.** 휴대폰 항목은 제거한다(앞선 결정).
4. **계정 삭제 영역(화면)은 유지하고 동작을 삭제한다.** 버튼은 남기되 클릭해도 아무 일도 하지 않는다(`handleDeleteAccount`의 로컬 키 삭제·로그아웃 제거). 백엔드 탈퇴 API를 만든 뒤 별도로 연동한다.
5. **언어는 한국어 단일로 고정한다.** 언어 선택 UI(한/영/일/중)를 제거하고 `lang="ko"`로 고정한다.

**수정 방향 (이전 합의 유지)**
6. 비밀번호 변경은 이번 이슈에서 손대지 않는다. 백엔드 API가 생긴 뒤 별도 이슈로 진행한다.
7. 임시 숨김·"준비 중" 표시·기존 저장 키 마이그레이션은 하지 않는다.

**구현 시 판단할 사항 (사용자 지정 없음, 구현자가 최소 변경으로 결정)**
- handle(사용자 이름) 필드는 서버에서 바꿀 수 없으므로 편집 불가 표시로 두거나 제거한다. 편집이 가능한 채로 남으면 안 된다(사이드바 프로필 링크가 오염됨).
- email 빈 칸 필드도 저장 대상이 아니므로 입력 불가(읽기 전용)로 둘지 확인한다. 어디에도 저장되지 않는 입력란이 편집 가능하면 같은 문제가 반복된다.
- 설정에 남는 것이 테마뿐이면 "변경사항 저장" 버튼과 토스트가 필요한지 판단한다. 로컬 테마 적용에는 즉시 반영이 자연스럽다. 서버에 저장되지 않는 값에 "저장되었습니다"를 표시하지 않는다.
- `gamerin_user_settings`에 테마만 남게 되면 별도 키 `gamerin_theme`과의 관계를 정리한다. `gamerin_theme`은 `src/app/layout.tsx:43`의 초기 테마 스크립트도 읽으므로 키를 바꾸면 함께 고친다. 남기는 저장 값은 `JSON.parse`(`user-settings.ts:87`, 현재 try/catch 없음) 예외 처리를 넣는다.
- 계정 삭제 버튼 옆 안내문 "현재 프론트에 저장된 로그인 정보, 프로필 이미지, 설정값을 삭제합니다."(`settings/page.tsx:226`)와 확인 문구(`:138`)는 동작을 지우면 사실과 달라진다. 실제 동작과 맞게 문구를 바꾼다(구체 문구는 구현 시 정함).

**범위·파일 (현재 코드 기준)**
- `src/app/(app)/settings/page.tsx`: 섹션 목록(`:350-353`의 계정/프라이버시/알림/테마·언어), 계정 정보(`:151-188`), 비밀번호(`:193`, 변경 없음), 위험 영역(`:220-238`, 안내문 `:226`, 버튼 `:229-235`), 프라이버시(`:253`)·알림(`:285`)·언어(`:334`) 섹션, `handleSave`(`:105-120`), `handleDeleteAccount`(`:137`)

- **메모(재개용)**: `/admin/settings`(`AdminSettingsScreen.tsx`)는 서비스 정책(서비스 이름, 신규 회원가입 허용, 점검 모드), 제재 정책(기본 제재, 신고 검토 기한), 자동화(신고 누적 자동 숨김, 임계값, 새 신고 알림), 운영·보안(관리자 2단계 인증 필수) 9개 항목을 React state로만 관리한다. "변경사항 저장"은 `setSavedSettings`만 호출하고 API가 없다. 선택지는 화면 삭제 또는 항목을 골라 백엔드 연동이다.

### A-3. HTTPS·HSTS (도메인 배포) — 2개 이슈로 분리

- **상태**: 방향 확정 (사용자 결정, 2026-10-01)
- **원칙**: 개발 중인 프로젝트이므로 임시 처리·하위호환은 하지 않는다.

**배경**
`next.config.ts`가 `NODE_ENV === 'production'`이면 HTTPS일 것이라고 가정하고 TLS 전제 헤더를 붙인다. 앱은 자기가 HTTP로 노출되는지 HTTPS로 노출되는지 알 수 없다. `upgrade-insecure-requests`는 CSS·JS·이미지 등의 HTTP 리소스 요청과 같은 호스트로의 HTTP 탐색을 HTTPS로 승격할 수 있어, HTTPS 입구가 없는 서비스의 자원 로드를 깨뜨릴 수 있다(현재는 주석 처리 상태, "배포시 주석 해제" 메모가 있어 되살릴 위험이 있다). 모든 외부 링크 탐색까지 승격하는 것은 아니다. HSTS(`max-age=63072000; includeSubDomains; preload`)는 HTTPS 응답을 통해 적용되면 마지막 수신부터 최대 2년간 해당 호스트의 HTTPS 접속을 강제하며, HTTP 응답의 HSTS는 적용되지 않는다. nginx는 `listen 80`뿐이라 TLS가 없다. 두 헤더는 빌드 타임에 `routes-manifest.json`으로 고정되므로 변경하려면 프론트 이미지를 리빌드해야 한다.

**확정한 접속 구성 (사용자 결정)**
- **배포는 구입한 도메인 `gamerin.live`(`https://gamerin.live`) 하나만 대상으로 한다**(도메인 확정, 2026-10-01). TLS는 nginx 앞단의 Caddy가 종단하고, HSTS도 Caddy에서만 낸다.
- **Tailscale(`tailscale serve`, `https://기기명.tailnet.ts.net`)은 맥에서의 모바일 테스트용이며 배포 설정에서 고려하지 않는다**(사용자 결정, 2026-10-01). 코드·nginx·compose에 ts.net 전용 설정을 넣지 않는다.
- 배포 접속은 HTTPS이므로 refresh 쿠키는 `REFRESH_COOKIE_SECURE=true` 하나로 맞춘다. **메시지 SSE stream-token 쿠키는 별도 설정**이다: `app.auth.sse.stream-token-cookie-secure`의 기본값이 `false`(`SseStreamTokenService.java:33`)이고 `docker-compose.yml`·`application-prod.yaml` 어디에서도 지정하지 않아, 지금 구성은 HTTPS에서도 이 쿠키에 `Secure`가 붙지 않는다. A-3b에서 이 값도 `true`로 지정한다.

#### A-3b. [docker] 도메인 배포용 TLS 입구

- **저장소**: docker (nginx, compose). backend 코드 변경은 없다(환경변수만 변경).
- **담당**: A (레포 이슈 DK-1)
- **선행 조건**: A-3a(프론트 헤더 삭제 후 이미지 리빌드)가 먼저 반영돼 있어야 한다. 도메인은 `gamerin.live`로 확정됐다.
- **참고**: 컨테이너 기동·재시작은 승인 없이 가능하지만 `deploy.sh` 등 배포 스크립트 실행·실제 배포는 사용자 승인 후 수행

**수정 방향**
1. **도메인 입구: Caddy를 nginx 앞에 둔다**(사용자 결정, 2026-10-01). 구입한 도메인의 DNS를 서버로 연결하고, Caddy 컨테이너가 80/443을 받아 TLS를 종단한 뒤 nginx:80으로 넘긴다(`reverse_proxy nginx:80`). 인증서 발급·갱신과 HTTP→HTTPS 리다이렉트는 Caddy가 자동으로 처리하며, 인증서 저장용 볼륨(`/data`)을 둔다. nginx는 호스트 포트를 공개하지 않고 Caddy만 공개한다. `docker/Caddyfile.example`은 호스트 직설치 기준으로 프론트(`127.0.0.1:3000`)와 API 서브도메인(`127.0.0.1:8080`)을 나누는 예시라 이 구성과 달라 새로 작성한다.
2. **HSTS는 Caddy의 도메인 블록에서만** 낸다(`header Strict-Transport-Security ...`). `max-age=300` → `86400` → `31536000`으로 단계적으로 올린다. `includeSubDomains`는 같은 도메인의 다른 서브도메인이 모두 HTTPS일 때만, `preload`는 제출 계획이 없으면 붙이지 않는다.
3. `upgrade-insecure-requests`는 앱에서 삭제하므로(A-3a) 필요 시 Caddy에서만 추가한다. 기본은 추가하지 않는다. HSTS는 해당 호스트의 HTTP 접속을 HTTPS로 강제하고, `upgrade-insecure-requests`는 문서의 HTTP 리소스 요청도 승격하므로 같은 기능으로 취급하지 않는다.
4. **외부 Host·Proto·Port·클라이언트 IP 전달**: 현재 `nginx/default.conf:14-16`은 `X-Forwarded-Host $host`, `X-Forwarded-Port $server_port`, `X-Forwarded-Proto $scheme`을 사용한다. 백엔드·Next가 외부 주소(`https`, 443, 도메인)를 받도록 한다. Caddy 뒤의 nginx가 받는 값은 `http`/80이므로 Caddy에서 온 요청에 한해 Caddy가 보낸 `X-Forwarded-Proto/Host`(포트 443)를 신뢰해 전달하고, 신뢰 경계 밖의 `Forwarded`/`X-Forwarded-*`는 제거하거나 덮어쓴다. 업로드 rate limit이 `$binary_remote_addr` 기준(`default.conf:1-2`)이므로 `real_ip`(`set_real_ip_from` Caddy 컨테이너 네트워크, `real_ip_header X-Forwarded-For`)로 실제 클라이언트 IP를 복원한다(복원하지 않으면 전체 사용자가 하나의 IP로 합산된다). 로컬(Caddy 없음)에서는 기존처럼 nginx 자신의 값이 쓰이게 한다. `location /`(`:66-70`)에는 `Upgrade`/`Connection`용 `proxy_set_header`가 있어 상위 `proxy_set_header` 설정을 상속하지 않으므로, 필요한 Host·Forwarded 헤더 설정을 이 location에도 적용한다([nginx 상속 규칙](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_set_header)).
5. 업로드(`/api/v1/posts`, `/api/v1/users/me/profile-images`)와 SSE(`/api/v1/messages/stream`) location의 크기 제한·rate limit·buffering off·timeout 1h·프록시 헤더가 Caddy를 거쳐도 그대로 적용되는지 확인한다. Caddy는 기본 본문 크기 제한이 없어 nginx 제한(530m 등)이 그대로 적용되는지, SSE(`text/event-stream`)가 버퍼링 없이 흐르고 1시간 연결이 Caddy에서 끊기지 않는지 확인한다.
6. 로컬 개발(`http://localhost`)이 계속 동작하도록 Caddy 서비스와 nginx 포트 비공개는 배포 환경에만 적용한다(compose override 또는 profile. 방법은 구현 시 정한다). nginx `default.conf`는 로컬과 배포가 같은 파일을 쓴다.

**배포 환경 설정 (비밀 설정 파일은 읽지 않음)**
- `REFRESH_COOKIE_SECURE=true` 유지(compose 기본값 `true`), `REFRESH_COOKIE_SAME_SITE`(기본 `Lax`) 적정성 확인.
- **메시지 SSE stream-token 쿠키 `Secure` 지정**: `app.auth.sse.stream-token-cookie-secure` 기본값 `false`, compose 미전달. **docker compose 환경변수로 지정한다**(사용자 결정, 2026-10-01): backend 서비스에 `APP_AUTH_SSE_STREAM_TOKEN_COOKIE_SECURE=true`(Spring relaxed binding)를 refresh 쿠키 설정과 같은 위치에 추가한다.
- **`FRONTEND_BASE_URL=https://gamerin.live`**(사용자 결정, 2026-10-01). `OAuth2SuccessHandler`의 로그인·소셜 가입 완료 복귀와 `PasswordResetMailService`의 비밀번호 재설정 링크가 이 주소를 기준으로 한다. `CORS_ALLOWED_ORIGINS`에도 도메인을 넣는다.
- Google OAuth 콘솔 redirect URI에 `https://gamerin.live/login/oauth2/code/google`을 등록한다. 백엔드는 `redirect-uri`를 따로 설정하지 않아 요청 호스트 기준 Spring 기본값(`{baseUrl}/login/oauth2/code/{registrationId}`)을 쓰므로, 위 4번의 Host·Proto 전달이 맞아야 `https://gamerin.live`으로 생성된다.
- `NEXT_PUBLIC_API_BASE_URL` build arg: nginx 상대경로 방식이면 빈 값. 빌드 타임 변수이므로 변경 시 프론트 이미지 리빌드.
- CSP `connect-src`/`img-src`/`media-src`가 도메인에서 문제없는지(`NEXT_PUBLIC_API_BASE_URL`이 비어 있으면 `'self'`로 충분).

**범위·파일**
- 신설: `docker/Caddyfile`(도메인, `reverse_proxy nginx:80`, HSTS 헤더)
- `docker/nginx/default.conf` (`:1-2` rate limit, `:6` server_name, `:11-16` Host·Forwarded 헤더, `:66-70` 프론트 location, `real_ip` 설정)
- `docker/docker-compose.yml` (Caddy 서비스·인증서 볼륨, nginx 포트 비공개, 환경변수 `:58-66`: `FRONTEND_BASE_URL`, `CORS_ALLOWED_ORIGINS`, SSE stream-token 쿠키 `Secure`), 배포 전용 override·profile(6번)
- 배포 문서에 Caddy 구성과 도메인 DNS 설정 절차 반영(갱신 필요 여부 보고)

**완료 조건**
- `https://gamerin.live`에서 스타일·이미지·로그인·새로고침 후 로그인 유지·업로드·SSE가 동작한다.
- `http://gamerin.live`이 `https://`로 리다이렉트되고, 응답에 HSTS가 있으며 `max-age`가 단계적 값이다.
- refresh 쿠키와 SSE stream-token 쿠키가 모두 `Secure`로 발급된다.
- 백엔드·Next에 Host·Proto·Port가 외부 접속 주소대로 전달되고, 생성되는 URL에 내부 호스트나 잘못된 `:80`이 없다. OAuth의 `redirect_uri`가 `https://gamerin.live/...`이다.
- Google 소셜 로그인이 도메인에서 완료되고 복귀 후 `/auth/me`와 새로고침 후 로그인 유지가 동작한다. 비밀번호 재설정 메일 링크가 도메인 주소로 생성된다.
- 업로드 rate limit이 실제 클라이언트 IP별로 동작한다.
- 로컬 `http://localhost` 개발 환경이 기존처럼 동작한다.
- `docker compose --env-file .env config --quiet` 통과, nginx 설정 검사(`nginx -t`)와 Caddy 설정 검사(`caddy validate`) 통과.

**주의**
- 잘못 설정한 HSTS는 되돌리기 어렵다. `max-age`를 처음부터 길게 잡지 않는다.

### A-4. 회원가입 검증·핸들 규칙 통일 — 2개 이슈로 분리 (약관 UI는 A-4c 보류)

- **상태**: 방향 확정 (사용자 결정, 2026-10-01)
- **원칙**: 개발 중인 프로젝트이므로 기존 핸들·데이터와의 호환 처리는 하지 않는다.

**배경**
프론트 회원가입 검증이 서버(`SignUpRequest`)보다 느슨해 프론트를 통과한 값이 서버 400으로 거절된다. 핸들 규칙은 일반 가입·소셜 가입·멘션 파서 세 곳이 서로 다르다.

| 위치 | 현재 규칙 |
|---|---|
| 일반 가입 `SignUpRequest.handle` | `^[a-z0-9._]+$`, 4~20자 (점 허용) |
| 소셜 가입 `SocialSignUpRequest.handle` | `^[a-z0-9_]{3,20}$` (점 불가) |
| 멘션 파서 `MentionParser` | 문자 `[a-z0-9._]`, 3~20자, 문장 끝 점(`@abc.`)을 떼어 가며 후보 탐색 |

**확정한 통일 규칙 (사용자 결정): 방안 1**
- **핸들: `^[a-z0-9_]{3,20}$`** (영문 소문자·숫자·밑줄, 3~20자, 점 불가). 소셜 가입 규칙이자 멘션 파서 최소 길이(3)와 일치하고, 점이 없어 멘션 파싱의 문장 끝 점 모호성이 사라진다.
- 서버 검증이 최종 기준이며 프론트는 같은 규칙을 사전 안내용으로 적용한다.

**현재 서버 규칙 (일반 가입·소셜 가입을 구분)**
| 항목 | 규칙 |
|---|---|
| 닉네임 | 일반 가입은 `@NotBlank` + `@Size(min = 2, max = 20)`. 소셜 가입은 `@NotBlank`만 있어 DTO에 길이 제한이 없음 |
| 이메일 | 일반 가입은 필수, `@Email` (검증 후 서비스에서 trim·소문자 정규화). 소셜 가입은 가입 세션의 provider 이메일 사용 |
| 비밀번호 | 필수, 8~20자, 영문·숫자·특수문자를 모두 포함 (`^(?=.*[A-Za-z])(?=.*\d)(?=.*[^A-Za-z\d]).+$`) |
| 비밀번호 확인 | 일반 가입은 필수, 서버에서 일치 검사 |
| 비밀번호 재설정 `ResetPasswordRequest.newPassword` | 위 비밀번호 규칙과 동일 |
| 약관·개인정보 동의 | 일반·소셜 모두 `Boolean` + `@AssertTrue`만 적용. `false`는 거절하지만 누락·`null`은 검증 통과하며 값은 저장하지 않음 → A-4c |

비밀번호 규칙은 일반 가입·비밀번호 재설정에 적용되며, 소셜 가입 요청에는 비밀번호 필드가 없다.

#### A-4a. [backend] 일반 가입 핸들 규칙을 소셜과 통일하고 소셜 닉네임 길이 검증 추가

### B-3. Enter 키·form·autocomplete (로그인·회원가입·댓글)

- **상태**: 방향 확정 (사용자 결정, 2026-10-01)
- **저장소**: frontend
- **담당**: 로그인·회원가입 부분은 A(레포 이슈 FE-2, A-4b와 같은 PR. 같은 파일 `login/page.tsx`를 수정하므로 충돌 방지), 댓글 부분은 B(레포 이슈 FE-7, 같은 `PostDetail.tsx`를 수정하는 B-4·B-7·C-2와 한 사람에게 모음).

**배경**
앱 전체에서 Enter 처리가 거의 없다. DM 입력창은 `<form onSubmit>`으로 해소됐지만(`messages/page.tsx:1570`, 단일 줄 `<input>`이라 Enter가 기본 제출) 로그인(`login/page.tsx`)에는 `<form>`이 없어 아이디·비밀번호 입력 후 Enter를 눌러도 아무 일이 없고 버튼 `onClick`만 동작한다(`:262-264` 로그인, `:390-392` 회원가입 다음 단계, `:471-473` 가입 완료). 입력에 `name`/`id`/`autocomplete`가 없어 브라우저·비밀번호 관리자가 자동 완성도 저장 제안도 하지 않는다. 모바일 키보드의 "이동/보내기" 버튼도 `<form>` 제출이 없으면 동작하지 않는다. 댓글은 `<textarea rows={3}>` + 버튼 `onClick`(`PostDetail.tsx:578-594`, `handleSubmitComment` `:253`)이다.

**범위 (사용자 결정): 로그인, 회원가입, 댓글 세 곳만.** 게시물 작성(`PostComposer.tsx`)은 이번 범위에서 제외한다.

**수정 방향**
1. **로그인**: 아이디·비밀번호 입력을 `<form onSubmit>`으로 감싸고 로그인 버튼을 `type="submit"`으로 한다. 입력에 `name`과 `autocomplete`(`username`, `current-password`)를 추가한다.
2. **회원가입**(단계별: 1단계 이름·이메일, 2단계 아이디·비밀번호): 각 단계를 `<form onSubmit>`으로 감싸고 "다음"과 "가입 완료" 버튼을 `type="submit"`으로 한다. `name`/`autocomplete`를 추가한다(`name`/`nickname`, `email`, `username`, `new-password`). 검증 로직은 A-4b의 `auth-validation.ts`를 사용한다.
3. **댓글**: 댓글 입력을 `<form onSubmit>`으로 감싸고 전송 버튼을 `type="submit"`으로 한다. `<textarea>`는 Enter가 줄바꿈이라 form만으로는 Enter 제출이 되지 않으므로, **Enter = 전송, Shift+Enter = 줄바꿈**을 키 처리로 추가한다(DM과 같은 관례). 한글 입력 조합 중(`event.nativeEvent.isComposing`)에는 Enter를 전송으로 처리하지 않는다. 전송 중·빈 입력일 때는 기존처럼 제출을 막는다.
4. 제출 중 중복 동작 방지(`submittingComment` 등 기존 상태)를 유지한다.

**구현 시 확인할 사항**
- 댓글 Enter 동작은 Enter 전송/Shift+Enter 줄바꿈으로 확정했다(사용자 결정, 2026-10-01, DM 관례와 같음).

- 회원가입 단계 이동 시 `<form>` 제출이 의도치 않게 페이지를 새로고침하지 않도록 `preventDefault`를 확인한다.

**수정 방향 (사용자 결정)**
1. **상대 시간 한국어 표기 규칙(권장안)**: `formatRelativeTime`을 아래 규칙으로 바꾼다.
   | 경과 시간 | 표기 |
   |---|---|
   | 1분 미만 | `방금 전` |

#### B-5a. [frontend] 토스트·확인 다이얼로그 기반 구현

- **담당**: B (레포 이슈 FE-5)
- **선행 조건**: 없음. **B-5b보다 먼저 병합한다.**

**수정 방향**
1. **`ToastProvider` + `useToast()`**: 성공·오류·정보 토스트를 띄운다. 예: `toast.success(msg)`, `toast.error(msg)`, `toast.info(msg)`. 루트 `layout.tsx`의 다른 Provider(`AuthProvider` 등)와 같은 위치에 둔다(서버 컴포넌트·`'use client'` 경계를 유지하고 상위 레이아웃 전체를 클라이언트로 바꾸지 않는다).
2. **확인 다이얼로그**: `window.confirm`을 1:1로 대체할 수 있도록 Promise 기반 `useConfirm()`(예: `const ok = await confirm({ message, confirmLabel, cancelLabel, danger })`)과 공용 다이얼로그 컴포넌트를 만든다. 호출부는 `window.confirm(...)`을 `await confirm(...)`으로 바꾸는 최소 변경이 되게 한다.
3. **접근성 기본기 포함**: 오류 토스트 `role="alert"`, 성공·정보 `role="status"`/`aria-live="polite"`, 닫기 버튼에 한국어 `aria-label`. 자동 닫힘은 일정 시간 후 닫되 마우스 올림·키보드 포커스 중에는 멈추고 수동으로 닫을 수 있다. 확인 다이얼로그는 `role="dialog"`/`alertdialog`, `aria-modal`, 포커스 이동·복귀, Esc로 취소한다.
4. **UI 요구**: 다크 모드, 모바일(1024px 미만 하단 탭바와 겹치지 않는 위치, safe-area 고려. 알림 패널·모달이 탭바에 가려 잘리던 #81 유형 문제를 재발시키지 않는다), 한국어 문구. 여러 토스트 동시 표시 규칙(쌓기·최대 개수), 동일 메시지 중복 억제 여부, 위치·지속 시간·애니메이션은 구현자가 기존 디자인과 맞춰 정하고 PR 설명에 적는다. framer-motion을 쓰면 이 컴포넌트에서 reduced-motion 설정을 존중한다.
5. 새 컴포넌트는 기존 `ErrorToast.tsx`를 재사용하지 않는다. 단위·컴포넌트 테스트(표시, 자동 닫힘, `role`, 확인 Promise 해결, Esc 취소)를 추가한다.

**범위·파일**
- 신규: Toast Provider/훅/컴포넌트, Confirm 훅/다이얼로그. 위치는 기존 구조(`app/context`, `lib`, `app/home/components`)의 관례를 따르며 공용 컴포넌트 디렉토리 이동은 D-7(보류) 소관이다.

**완료 조건**

게시물 본문에서 `#해시태그`는 링크가 되지만(`HashtagText.tsx:5` `HASHTAG_PATTERN`) `@handle`은 평문이다. 백엔드는 멘션을 파싱해 `user_mentions`에 저장하고 멘션 알림(`notifications.mention_id`)을 보내므로(`MentionParser`, `MentionService`), "누가 나를 언급했습니다" 알림은 오는데 본문의 `@handle`을 눌러도 아무 일이 없다.

**확정한 방식 (사용자 결정)**
- **방안 1: 프론트가 규칙에 맞는 `@handle`을 모두 링크로 만든다.** 백엔드가 실제로 멘션으로 인식한 목록을 응답에서 받는 방식(방안 2)은 쓰지 않는다. 존재하지 않는 핸들도 링크가 되며 클릭하면 프로필의 "사용자를 찾을 수 없습니다" 화면으로 간다.
- **적용 범위: `HashtagText`를 쓰는 곳 전체 + 댓글 본문.** `HashtagText` 사용처(2026-10-01 조사)는 `Post.tsx:354`(게시물 카드: 피드, 검색 결과, 북마크, 프로필, 해시태그 목록 등 `Post`를 쓰는 모든 화면)와 `PostDetail.tsx:490`(게시물 상세 본문) 두 곳이다.

> 범위 메모: DM 메시지 본문은 범위에 포함하지 않는다(메시지 도메인에 멘션 처리 코드가 없다).

**수정 방향**
1. `HashtagText.tsx`가 해시태그와 함께 `@handle`도 파싱해 링크로 렌더링한다. 링크 대상은 `/profile/{handle}`(`encodeURIComponent` 적용)이다. 컴포넌트 이름은 바꾸지 않는다(이름 변경은 별도 구조 이슈).
   댓글 본문(`PostDetail.tsx:680`, 현재 `{comment.content}` 평문)은 같은 파서로 멘션만 링크로 렌더링한다. 해시태그를 끄는 prop을 `HashtagText`에 둘지 멘션 전용 렌더링을 둘지는 구현 시 정하되, 멘션 파싱 규칙은 한 곳(순수 함수)만 쓴다.
2. **멘션 규칙은 백엔드 `MentionParser`와 맞춘다.**
   - 핸들 문자: 영문 소문자·숫자·밑줄, 3~20자 (`[a-z0-9_]{3,20}`). 대문자는 멘션으로 인식하지 않는다(백엔드 `isValidHandle`이 소문자만 허용).
   - 시작 경계: 문장 시작·공백·유니코드 공백 뒤를 허용한다. 그 밖에는 앞 코드포인트가 문자·숫자·밑줄·`.`·유니코드 결합 문자이거나 `@`, `#`, `/`, `\`이면 멘션이 아니다(예: 이메일 `a@b.com`). 괄호·쉼표 등 나머지 문장부호 뒤는 서버처럼 허용한다(예: `(@abc)`, `,@abc`).
   - 끝 경계: 공백·허용된 문장부호는 링크에 포함하지 않는다. 뒤에 대문자·한글·숫자·밑줄·결합 문자 등이 붙은 후보를 유효한 핸들의 접두부만 잘라 링크로 만들지 않는다(예: `@abcD`, `@abc한`, 21자 이상 후보는 링크가 아님). 점 포함 후보와 문장 끝 점 처리는 아래 A-4a 조율 항목을 따른다.
   - 해시태그 패턴과 겹치지 않게 처리한다(`#`로 시작하는 태그 안의 `@`, URL 안의 `@` 등).

4. 접근성: 링크 텍스트는 `@handle` 그대로 두고 포커스 가능한 일반 링크로 둔다.

### B-8. `/` 인증 상태 분기와 UX 잔여 개선 (4개 항목)

**배경**

#### a. `/`를 인증 상태로 분기하고 308 영구 리다이렉트를 제거

- **지금**: `next.config.ts:116-123`의 `redirects`가 `/`→`/login`을 `permanent: true`(308)로 보낸다. 브라우저가 무기한 캐시하고, 로그인 상태에서도 `/`→`/login`→`/home`으로 한 번 더 돈다.
- **수정 방향 (사용자 결정)**: `permanent: false`(307)로 낮추는 데서 그치지 않고 **`/`에서 인증 상태로 분기한다.** 로그인된 사용자는 `/home`, 아닌 사용자는 `/login`으로 보낸다. 308 영구 리다이렉트(`next.config.ts`의 `/` redirect)는 제거한다.
- **구현 시 판단할 사항**
  - 인증 상태는 클라이언트 메모리(`AuthContext`, access token은 메모리 저장)와 HttpOnly refresh 쿠키로 결정된다. 구현 방식은 구현자가 정한다: (1) `/` 페이지를 클라이언트 컴포넌트로 만들어 `AuthContext`의 `isAuthReady`/`user`로 `router.replace`, (2) Next 미들웨어에서 refresh 쿠키 존재 여부로 분기(쿠키 존재가 유효한 로그인을 보장하지 않으므로 최종 판단은 기존 `(app)/layout.tsx` 가드가 한다. 쿠키 이름은 서버 설정값이므로 프론트가 알 수 있는지 확인). 프론트 인증 가드는 서버 인가를 대체하지 않는다는 원칙을 유지한다.
  - 클라이언트 방식은 인증 복원 동안 잠깐 빈 화면이 생길 수 있다. 사용자 결정으로 인증 복원 중 로딩 UI는 만들지 않으므로(아래 제외 표), 분기 중 표시는 최소한으로 한다.
  - **D-1과의 순서**: 병합 순서는 강제하지 않는다. D-1이 먼저 병합되면 이 이슈 반영 전까지 `next.config.ts`의 기존 redirect가 `/`를 처리하고, 이후 신규 `page.tsx` 또는 미들웨어로 인증 분기를 구현한다. 이 이슈가 먼저 병합되면 D-1은 `page.tsx`가 기본 템플릿인지 다시 확인해 새 인증 분기 페이지는 보존하고, 추가된 미들웨어와 308 제거도 되돌리지 않는다.
  - 로그아웃 후·세션 만료 후 `/` 진입, OAuth 복귀(`/auth/oauth-success`)와의 상호작용을 확인한다.
- **범위·파일**: `next.config.ts`(`:116-123`), `src/app/page.tsx` 또는 `src/middleware.ts`(신규), `(app)/layout.tsx` 가드(변경 없음 확인)
- **완료 조건**: 비로그인 상태 `/` → `/login`, 로그인 상태 `/` → `/home`으로 이동한다. 응답이 308이 아니며(307이거나 클라이언트 이동) 브라우저에 영구 캐시되지 않는다. 로그아웃 후 `/` 진입이 `/login`으로 간다.

#### b. 메시지 날짜 구분선

### C-1. 게시물 카드의 중첩 인터랙티브 구조 해소 (오버레이 링크 방식)

- **상태**: 방향 확정 (사용자 결정, 2026-10-01). **FE-7에서 카드 구조 변경의 마지막 단계로 진행한다.** 아래 선행 작업을 마친 뒤 C-1을 병합하고, 이후 D-8(오류 문구)과 D-9(다크 모드)를 진행한다.
- **저장소**: frontend
- **담당**: B (레포 이슈 FE-7)
- **선행 조건**: 아래 "진행 순서"의 이슈들이 먼저 병합돼 있어야 한다.
- **원칙**: 개발 중인 프로젝트이므로 하위호환·임시 처리는 하지 않는다.

**배경**
`Post.tsx:257-263`의 `<motion.article>`이 `role="button"`, `tabIndex={0}`, `onClick`(`handleOpenDetailFromCard` `:154`), `onKeyDown`(Enter·Space, `handleOpenDetailFromKeyboard` `:162`)으로 카드 전체를 하나의 버튼처럼 동작시킨다. 그 안에 프로필 링크, 해시태그 링크, 좋아요·댓글·리포스트·북마크·공유 버튼 등이 들어 있다. 카드 클릭 시 안쪽 요소를 무시하는 판별은 `shouldIgnoreCardOpen`(`:148`, `a, button, input, select, textarea, video, [data-card-open-ignore="true"]`)이다. 원문 측정에서 `/home`의 `role="button"` 카드 20개가 각각 7~9개의 인터랙티브 요소를 품었다(WCAG 4.1.2 위반). 스크린 리더는 카드 본문 전체를 버튼 이름으로 읽은 뒤 안의 버튼을 또 만나고, 키보드 사용자는 게시물 하나당 Tab을 6~7번 눌러야 다음 게시물로 간다.

**확정한 방향 (사용자 결정): 방안 2 — 카드 전체 클릭 UX를 유지하되 "게시물 열기" 오버레이 1개를 둔다.**

**수정 방향**
1. `<article>`에서 `role="button"`, `tabIndex`, `onClick`, `onKeyDown`을 제거하고 일반 컨테이너(`<article>`)로 둔다.
2. 카드 안에 **"게시물 열기" 오버레이 요소 하나**를 둔다. 카드 전체를 덮는 투명한 요소(`absolute inset-0`)이며 포커스 가능한 단일 상호작용(링크 또는 버튼)이다. 접근 가능한 이름은 구체적으로(예: `{작성자}님의 게시물 열기`) 한다. 카드를 누르면 지금처럼 상세로 이동한다(`onOpenDetail`).
3. 프로필 링크, 해시태그·멘션 링크, 액션 버튼 등 카드의 다른 인터랙티브 요소는 오버레이보다 위에 두어(`relative z-10` 등) 각자 동작하고 오버레이는 이들과 **중첩되지 않는 형제 요소**다. 텍스트 등 비상호작용 영역은 클릭이 오버레이로 전달되게(`pointer-events` 처리) 한다. 사용자가 본문 텍스트를 드래그 선택할 수 있어야 한다.
4. 키보드 동작은 오버레이 요소의 기본 동작으로 처리한다(링크는 Enter, 버튼은 Enter·Space). 카드당 Tab 정지는 기존 카드 컨테이너 1개가 오버레이 1개로 대체되며, 프로필 링크·액션 버튼을 유지하면 정지 수 자체는 줄지 않는다. 목표는 중첩 해소와 명확한 접근 가능한 이름·포커스 순서다.
5. `shouldIgnoreCardOpen`/`data-card-open-ignore` 기반의 클릭 위임 판별은 오버레이 구조로 대체돼 불필요해진다. 불필요해진 코드(및 `HashtagText.tsx`의 `data-card-open-ignore`)를 정리하되, 다른 곳의 사용 여부를 확인한 뒤 제거한다.
6. `onOpenDetail`을 쓰지 않는 사용처(상세 화면 등 `onOpenDetail`이 없을 때)는 오버레이를 렌더링하지 않는다. `onOpenComments`(댓글 버튼)는 기존 동작을 유지한다.
7. 비디오 등 자체 컨트롤을 가진 미디어(`video`)와 이미지 확대 같은 카드 내부 동작이 오버레이에 가려지지 않게 한다.

**구현 시 확인할 사항**
- 오버레이를 링크(`<a href>`)로 할지 버튼으로 할지는 호출부가 `onOpenDetail` 콜백(`router.push`)을 넘기는 현재 구조를 고려해 결정한다. 링크로 하면 새 탭 열기·링크 복사가 가능해지는 장점이 있고 `href` 계산이 필요하다.
- `whileHover={{ y: -4 }}`(framer-motion)와 오버레이·그림자 효과가 겹치지 않는지 확인한다. reduced-motion 처리는 C-4 제외로 이번 범위가 아니다.
- 카드 리스트(피드, 검색, 북마크, 프로필, 해시태그)에서 키보드 Tab 순서와 포커스 링이 자연스러운지 확인한다.
- 다크 모드·모바일(터치)에서 오버레이가 스크롤·탭 동작을 방해하지 않는지 확인한다.

**진행 순서 (같은 `Post.tsx`를 수정하는 이슈와의 충돌 방지)**
- 먼저 병합: **B-4**(`<time>`·문구), **B-5b**(`alert`/`confirm` 치환, `Post.tsx` 3곳), **B-6**(게시물 메뉴 훅), **B-7**(`HashtagText`·댓글 멘션), **B-3 댓글 부분**(`PostDetail.tsx` 댓글 form·Enter)

### C-2. 좋아요·리포스트·북마크 버튼의 접근 가능한 이름과 상태

- **상태**: 방향 확정 (사용자 결정, 2026-10-01). **FE-7의 하위 작업으로 관리하고, C-1보다 먼저 별도 PR로 병합한다.**
- **저장소**: frontend
- **담당**: B (레포 이슈 FE-7)
- **선행 조건**: frontend 공통 선행인 D-10·D-11 병합 후 진행 (C-1의 선행 하위 작업)
- **원칙**: 개발 중인 프로젝트이므로 하위호환·임시 처리는 하지 않는다.

**배경**
게시물 카드(`Post.tsx`)의 댓글·리포스트·북마크·공유 버튼에는 `aria-label`이 있는데(`:379,389,412,422`) **좋아요 버튼에만 없다**(`:362-372`, 내용이 아이콘과 숫자뿐이라 스크린 리더가 "0, 버튼"으로만 읽는다). 좋아요 여부를 알려 주는 `aria-pressed`도 없다. 리포스트·북마크는 상태에 따라 라벨 문구를 바꾸는 방식(`리포스트`/`리포스트 취소`, `북마크 저장`/`북마크 해제`)이라 `aria-pressed` 없이 라벨로만 상태를 전달한다. 같은 유형의 버튼이 게시물 상세(`PostDetail.tsx:524` 좋아요, `:541` 리포스트, `:553` 북마크)에도 있다.

**확정한 범위 (사용자 결정): 범위 2 — 좋아요 버튼이 있는 모든 곳, 리포스트·북마크 버튼의 상태 표시 점검 포함.** 대상은 `Post.tsx`와 `PostDetail.tsx`다. 같은 패턴의 버튼이 다른 파일에 있는지 구현자가 검색해 함께 정리한다.

**수정 방향**
1. **좋아요**: `aria-label`과 `aria-pressed={post.likedByMe}`를 추가한다. 개수가 이름에서 사라지지 않게 라벨에 개수를 포함하거나(예: `좋아요 12개`) 개수 텍스트가 별도로 읽히게 한다. 구체 문구는 한국어로 구현 시 정한다.
2. **리포스트**: 좋아요와 같은 토글 버튼이므로 **고정 라벨 + `aria-pressed`** 패턴으로 통일한다(상태에 따라 라벨 문구를 바꾸는 현재 방식과 `aria-pressed`를 동시에 쓰지 않는다). 리포스트 불가 상태(`!canRepostPost`)의 설명(`title`)은 유지하되 보조기기에도 전달되게 한다(구현 시 판단).
3. **북마크**: 버튼이 단순 토글이 아니라 컬렉션 저장 모달을 연다(`setCollectionModalOpen(true)`). 따라서 `aria-pressed`를 억지로 붙이지 않고, 현재 라벨 방식을 유지하되 모달을 여는 버튼임을 알리는 `aria-haspopup="dialog"` 추가 여부를 구현자가 판단한다. 북마크 상태가 보조기기에 전달되는지 점검하고 부족하면 보완한다.
4. **상세 화면과 일관**: `PostDetail.tsx`의 좋아요·리포스트·북마크 버튼도 카드와 같은 패턴으로 맞춘다.
5. 요청 중 중복 클릭 방지(`disabled`)가 보조기기에도 전달되는지(`disabled` 속성 유지) 확인한다. 별도 `aria-busy` 추가는 필수가 아니다.
6. 컴포넌트 테스트에 접근성 쿼리(`getByRole('button', { name, pressed })`)로 라벨·상태 검증을 추가한다.

**구현 시 확인할 사항**
- 라벨 문구가 B-4(화면 문구 한국어 통일)와 일관된다.
- 아이콘만 있는 버튼(북마크 등)의 기존 `aria-label`은 유지하고 중복 라벨이 생기지 않게 한다.
- 이 이슈는 **C-1(카드 구조 변경)보다 먼저** 병합한다. 같은 `Post.tsx`를 수정하는 B-4, B-5b, B-6과의 병합 순서는 자유지만 먼저 병합된 변경 위에서 rebase해 충돌을 해소한다.
- `Post.tsx`의 `whileHover`(reduced-motion)는 C-4 제외로 이 이슈에서 다루지 않는다.

**범위·파일**
- `src/app/home/components/Post.tsx` (`:362-372` 좋아요, `:386-405` 리포스트, `:407-420` 북마크)
- `src/app/home/components/PostDetail.tsx` (`:524-559` 좋아요·리포스트·북마크)
- 같은 패턴의 다른 파일(검색으로 확인)
- 관련 테스트(`Post`, `PostDetail`)

**완료 조건**
- 좋아요 버튼의 접근 가능한 이름이 "좋아요"(개수 포함)이고 `aria-pressed`가 좋아요 여부를 반영한다.
- 리포스트 버튼이 고정 라벨 + `aria-pressed`로 상태를 전달한다.
- 북마크 버튼의 상태와 모달을 여는 성격이 보조기기에 전달되는 방식이 정해져 적용된다.
- 카드와 상세 화면의 세 버튼이 같은 패턴이다.
- `npm run lint`, `npm test`, `npx tsc --noEmit` 통과.

- 일반 로그인·OAuth로 로그인한 사용자 객체에는 `role`/`status`가 비어 있고, 새로고침(앱 시작 복원)이 `/auth/me`로 채운다. 로그인 직후와 새로고침 후의 사용자 객체가 다르다.

- `auth-store.ts`의 refresh(`:389`)·logout(`:299`) `fetch`는 세션 코어 로직이므로 이 이슈의 중복 대상이 아니다. 단 OAuth 완료 화면은 `auth-store`를 거치지 않고 refresh를 인라인 `fetch`로 직접 호출한다(`oauth-success/page.tsx:23`). `auth-store.ts`는 세대 번호를 받는 `refreshAccessTokenResult(expectedGeneration)`(`:365`)를 이미 export한다.

**확정한 범위·방식 (사용자 결정)**
- **일반 로그인도 관리자 로그인처럼 항상 `/auth/me`를 다시 조회해 한 가지 출처로 통일한다**(요청이 1번 늘어난다). 로그인 응답의 사용자 정보는 쓰지 않는다(access token만 사용).
- **범위는 4개 흐름만**: 일반 로그인, 관리자 로그인, OAuth 완료, 앱 시작 복원. **회원가입, 소셜 가입 완료, 아이디 찾기, 비밀번호 찾기·재설정은 이 이슈에서 제외한다**(A-4b·B-3 소관).

**수정 방향**
1. `src/lib/auth-api.ts`를 신설한다. 예시 구성(이름·시그니처는 구현 시 확정):
   - `loginWithPassword(handle, password)`: 로그아웃 완료 대기 → `POST /api/v1/auth/login` → access token 저장 → `/auth/me` 조회 → 사용자 객체 반환
   - `completeOAuthSession()`: refresh → access token 저장 → `/auth/me` 조회 → 사용자 객체 반환. refresh는 `auth-store.ts`의 기존 export `refreshAccessTokenResult`를 재사용하고 `auth-api.ts`에 refresh `fetch`를 새로 쓰지 않는다(`auth-store.ts` 변경 금지와 완료 조건 "refresh는 `auth-store.ts`에만"을 함께 만족하기 위함.)
   - `fetchMe()`: `/auth/me` 조회와 응답 형식 검증(`userId`, `handle`, `nickname` 문자열)
   - `toAuthUser(me, base?)`: `/auth/me` 응답을 앱의 사용자 객체로 만드는 **매핑 단 하나**. `role`/`status`를 항상 채우고, `gameTier`·`bio` 기본값을 한곳에서 정한다. 앱 시작 복원은 저장된 사용자 필드를 보존하도록 `base`로 병합한다.
2. **안전장치를 모듈 안에 둔다**: 세대 가드(요청 전후 `getAuthGeneration`/`assertCurrentAuthGeneration`, 오래된 응답은 `AbortError`로 버림), 차단 계정 검사(`isBlockedAccountResponse`, `isBlockedAccountStatus`), 로그아웃 진행 대기(`waitForLogoutCompletion`)를 4개 흐름이 같은 방식으로 적용받게 한다.
3. 4개 흐름이 이 모듈을 쓰도록 바꾼다. 화면은 성공·실패 표시와 이동만 맡는다.
   - `login/page.tsx`의 `handleLocalLogin`
   - `AdminLoginForm.tsx`의 `handleSubmit`(관리자 역할 검사는 반환된 사용자의 `role`로 화면/모듈에서 수행)
   - `auth/oauth-success/page.tsx`
   - `AuthContext.tsx`의 `bootstrapAuth`
4. `AuthContext`는 세션 상태 전이(`login`, `logout`, `updateUser`)에 집중하고 네트워크 세부 구현은 `auth-api.ts`가 맡는다. 현재 `AuthContext.tsx` 내부 `User` 타입이 export되지 않았다면 모듈이 쓸 수 있게 공용 위치로 옮기거나 export한다.
5. 인증이 필요 없는 공개 호출(`/auth/login`)은 `apiRequest`가 아니라 `fetch`로 하는 기존 방침(CLAUDE.md의 공개 인증 화면 규칙)을 따른다. `/auth/me`는 이미 쓰는 `apiRequest`(401 시 refresh 1회 재시도, 최종 실패 시 세션 종료) 방식과 맞추는 쪽을 우선 검토한다.
6. 보안 규칙을 유지한다: access token은 메모리에만 저장하고 localStorage·URL에 두지 않는다. 프론트 가드가 서버 인가를 대체하지 않는다. `credentials: 'include'`로 refresh cookie를 사용한다.
7. 단위 테스트(`lib/__tests__/auth-api.test.ts`)를 추가한다: 로그인 성공·실패, 차단 계정, 세대 변경으로 응답 폐기, `/auth/me` 형식 오류, 매핑(`role`/`status`/기본값), refresh 거절·일시 장애. 기존 `login`, `AdminLoginForm`, `oauth-success`, `AuthContext` 테스트를 갱신한다.

**구현 시 판단할 사항**
- `gameTier`·`bio` 기본값: 현재 일반 로그인·OAuth는 `'Unranked'`(`login/page.tsx:156`, `oauth-success/page.tsx:77`), 관리자 로그인은 `''`(`AdminLoginForm.tsx:97`)다. 어느 값으로 통일할지 정한다. `Header.tsx:214`는 `user.gameTier`를 그대로 표시하고 `Sidebar.tsx:105`는 `|| 'Unranked'`로 대체한다. 값을 `''`로 통일하면 Header에 빈 칸이 표시될 수 있으므로 표시 쪽 처리를 함께 확인한다(B-4의 `Unranked` 표시 한국어화와 조율). `bio`는 서버 인증 응답에는 없지만 프로필 화면이 `updateUser({ bio, … })`로 채운다(`profile/[userId]/page.tsx:439,732`). 앱 시작 복원의 `base` 병합이 이 값을 보존하는지 확인한다.

**확정한 범위 (사용자 결정): 범위 2**
- **포함**: 인증 오류 판별을 `status`/`reason` 기반으로 통일하고 문자열 매칭을 삭제한다. 영어 fallback 메시지를 한국어로 통일한다.

**수정 방향**
1. **공통 인증 오류 판별**: `api-client.ts` 쪽에 `isAuthError(error)`(이름은 구현 시 확정)를 둔다. `ApiError`의 `status`(401)나 `reason`(`unauthenticated`/`blocked`/최종 401)을 기준으로 판별한다. 필요하면 `ApiError`에 `reason`을 담거나 `AuthRequiredError`(ApiError 하위)를 둔다. 각 모듈 `toError`가 `unauthenticated`/401 상황에서 이 오류를 던지게 한다.
2. **문자열 인증 판별 삭제**: `isMentoringAuthError`, `isMessageAuthError`, `isAuthRequiredError`를 공통 `isAuthError`로 대체하고 사용처(`messages/page.tsx` 9곳, `mentoring/page.tsx:383,519`)를 바꾼다. `MentoringAuthError`는 공통 오류로 흡수하거나 유지 여부를 구현 시 정한다(유지한다면 문자열 분기는 제거).
3. **일반 `Error`를 던지는 모듈을 `ApiError`로**: `message-api`, `community-search-api`, `mileage-api`, `notification-api`의 `toError`가 `ApiError`(상태 포함)를 던지게 해 호출부가 `status`로 판별할 수 있게 한다. `AuthContext.tsx:126`도 한국어 메시지로 맞춘다.
4. **인증 필요 문구는 한 상수로** 통일한다(현재 `Authentication is required or the token has expired.`, `Authentication is required. Please sign in again.`, 한국어 `로그인이 필요하거나 인증이 만료되었습니다. 다시 로그인해주세요.` 등 여러 변형). 예: 기존 한국어 문구를 공통 상수로 쓴다.
5. **영어 fallback 한국어화**: 위 목록의 영어 메시지를 일관된 한국어 문구로 바꾼다(문체 예: `○○하지 못했습니다.`). 서버가 `message`를 주면 그것을 우선하는 기존 규칙은 유지한다. 구체 문구는 구현 시 정하고 PR 설명에 목록을 남긴다. 번역 체계(i18n)는 만들지 않는다.
6. **마일리지 부족·리뷰 중복 판별은 문자열 기반을 유지**하되 백엔드의 현재 한국어 메시지 기준으로 정리하고 영어 대응어 분기는 삭제한다(백엔드 메시지가 한국어이므로). 가능하면 `ApiError`의 `status`(400/409)를 함께 확인해 오탐을 줄인다. 이 판별은 백엔드 오류 코드가 도입되면(후속) 코드 기반으로 바꾼다는 점을 코드 주석이 아닌 이 이슈에 남긴다.
7. 단위 테스트: `isAuthError`(401, `unauthenticated`, `blocked`, 일반 `Error`는 false), 각 모듈의 `toError` 결과 타입·상태·메시지. 영어 메시지를 단언하던 기존 테스트(`lib/__tests__/message-api.test.ts`, `community-search-api.test.ts`, `mentoring-mileage-api.test.ts`, `notification-api.test.ts` 등)를 한국어로 갱신한다.

**구현 시 확인할 사항**

2. **`.gitattributes`를 함께 추가**한다: `* text=auto eol=lf` 등으로 팀원의 로컬 설정(`autocrlf`)과 무관하게 저장소 내 파일이 LF로 유지되게 한다. 이진 파일은 `binary`로 둔다. 세부 규칙은 구현 시 정하고 PR 설명에 적는다.

5. **기능 변경과 분리된 단 하나의 전용 커밋**으로 만든다(커밋 메시지 예: `chore: 줄바꿈을 LF로 통일하고 BOM 제거`). 다른 변경(포맷터 적용, 따옴표·import 정리)을 섞지 않는다.

7. 팀 지침 문서(`AGENTS.md`, `CLAUDE.md`)에 EOL·BOM 규칙을 적을지는 구현 시 판단한다. 적는다면 두 파일을 함께 갱신한다.

### 의존성·조율 (정확한 규칙)

1. **frontend 공통 선행**: D-10 → D-11을 별도 PR로 먼저 병합한다. D-11은 D-10 이후의 LF 기준 파일에서 작업하고, 나머지 frontend 브랜치는 두 변경이 모두 반영된 파일 위에서 시작한다. BE-1은 이 조건과 독립적으로 병행할 수 있다.
2. **같은 사람 안의 순서**: A-4a → A-4b(병합 순서), A-5a → A-5b, A-3a → A-3b, A-4b+B-3 → D-2 → D-6, B-5a → B-5b, B-4·B-5b·B-6·B-7·B-3(댓글)·C-2 → C-1, A-1·B-1·B-8 → D-4a → D-4b → D-8.
3. **사람 사이의 순서**: 위 선행 조건 표를 적용한다. 특히 **FE-7 전체(C-1 포함) → D-8 → D-9** 순서를 고정한다. 대기 조건은 하위 작업의 PR 병합을 기준으로 판단하며 레포 이슈 전체 종료를 기다리지 않는다(FE-7은 모든 하위 작업의 병합이 필요).
4. **같은 PR**: A-4b + B-3의 로그인·회원가입 부분(`login/page.tsx`), B-1 + B-8(`home/page.tsx`).
5. **병렬 개발 시 병합 조율**: 아래 조합은 추가 시작 대기를 강제하지 않는다. 같은 파일을 수정하면 먼저 병합된 변경 위에서 rebase하고, 뒤에 병합하는 PR이 두 작업의 완료 조건과 관련 회귀 테스트를 함께 확인한다. 텍스트 충돌이 없어도 먼저 반영된 기능이 되돌아가지 않았는지 확인한다. 실제 병합·rebase 실행은 각 저장소 지침과 승인 범위를 따른다.
   - B-5b(B) ↔ A-4b·B-3(로그인·회원가입)(A): `login/page.tsx`, `auth/social/complete/page.tsx`. 토스트 전환과 입력 검증·로그인 흐름을 함께 유지하고 `alert`/`confirm`을 재도입하지 않는다.
   - B-5b(B) ↔ A-5b(A): `mentoring/page.tsx`. 확인 다이얼로그와 게임 목록 API 연동을 함께 유지한다.
   - B-5b(B) ↔ B-2·B-1·B-8(C): 프로필·검색·홈 화면. 토스트 전환과 프로필 표시·탭 URL·스크롤 동작을 함께 유지한다.
   - B-4(B) ↔ A-1·B-2·B-1·B-8·D-4a/D-4b(C), A-5b(A): 프로필·검색·메시지·멘토링·피드 목록 화면. 한국어 문구·상대 시간과 목록 훅·탭·게임 연동 기능을 함께 유지한다.
   - D-4a(C)가 `PostDetail.tsx`를 포함할 경우 ↔ FE-7(B): 좋아요 훅 적용과 접근성·메뉴·댓글 동작을 함께 유지한다. 포함 여부와 해당 파일의 병합 순서는 양 담당자가 공유한다.
   - D-9b(A) ↔ B-5a(B): `layout.tsx`의 시스템 폰트 변경과 Toast/Confirm Provider 연결을 함께 유지한다.
   - D-3(A) ↔ B-4(B): `feed-api.ts`. 공용 타입·`toNumber` 정리와 `formatRelativeTime` 한국어 규칙을 함께 유지한다.
